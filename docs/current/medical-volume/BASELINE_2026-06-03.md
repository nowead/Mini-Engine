# M3-3 v0 + M4 v1 Baseline Measurements — 2026-06-03

**Build**: commit `965926f` (D3 Phase 1).
**GPU**: NVIDIA GeForce RTX 4070 (Vulkan native).
**OS**: Windows 11 Home.
**측정 도구**: ImGui 패널의 `Brick storage` 섹션 + `Render CPU` (steady_clock,
EMA α=0.1) + ImGui IO 프레임 시간.

이 문서의 목적: **M3-3 v0 + M4 v1 위에서, 현재 시점의 정직한 수치**를 기록한다.
M3-3 v1 streaming(Step E) 작업 후 같은 표를 다시 채워 "얼마나 좋아졌는가"의
근거점으로 사용한다.

## 2. Brick 저장 통계 (모드 무관)

| Case | Page grid | Atlas grid | Used / Total | Atlas live MB | Atlas alloc MB | Saving vs dense |
| --- | --- | --- | --- | --- | --- | --- |
| 1 (96³)  | 2×2×1 (4 bricks) | 2×2×1 (4 slots) | 3/4 (75.0%) | 1.6 | 2.2 | **−160.0%** |
| 2 (256³) | 4×4×4 (64 bricks) | 4×4×4 (64 slots) | 8/64 (12.5%) | 4.4 | 35.1 | **−9.7%** |
| 3 (1024×1024×512) | 16×16×8 (2048 bricks) | 8×8×8 (512 slots) | 304/512 (59.4%) | 166.7 | 280.8 | **+72.6%** |

### 핵심 발견: brick atlas는 작은 볼륨에서 **손해**

이 표가 baseline의 가장 중요한 결과다:

- 96³: 0.8 MB → 2.2 MB **(2.8배 증가)**
- 256³: 32 MB → 35.1 MB **(약간 손해)**
- 1024³+: 1024 MB → 280.8 MB **(72.6% 절감)** ← 헤드라인

**왜 작은 볼륨에서 손해인가**:

1. **Halo 오버헤드**: 모든 brick이 64³ → 66³로 저장되어 voxel 수가 (66/64)³ = 9.2%↑
2. **Atlas 사전 할당**: atlas 그리드 안의 빈 slot도 메모리 잡음. 96³의 경우
   pageGrid (2,2,1) = 4 brick인데 atlas (2,2,1) = 4 slots × 66³ × 2B = 2.2 MB.
   원본 0.8 MB보다 큼.
3. **R16Float 저장**: 원본 NIfTI는 int16 (2B/voxel)지만 atlas는 R16Float (2B/voxel)
   — 같은 크기지만 dense 비교 대상이 16비트 정수 시리즈라면 차이는 halo 오버헤드만.

**crossover 지점**: 약 256³ 근방에서 손익 분기. 그 이상에서 sparsity로 빠르게 이득.

### 1024³의 실제 메모리 동작

- 2048 virtual brick 중 304개만 non-empty (sphere 모양 → 모서리 brick은 air)
- 304는 atlas cap (8,8,8) = 512에 여유롭게 fit
- live(166.7 MB)는 used slot 만, allocated(280.8 MB)는 atlas 전체 텍스처 크기
- live/alloc 비율 = 59.4% = used/total — 항상 일치 (slot 단위 동일 크기)

→ 실제 GPU VRAM은 alloc 기준. **1 GB → 281 MB**. M3-3 v1 streaming이 없어도
이미 실용적.

## 3. 렌더 성능

| Case | Mode | FPS | ms/frame | Render CPU (ms) |
| --- | --- | --- | --- | --- |
| 1 (96³) | Lambert + shadow | 462.7 | 2.16 | 0.29 |
| 1 (96³) | Path-traced (SPP 8) | 471.3 | 2.12 | 0.33 |
| 2 (256³) | Lambert + shadow | 1021.4 | 0.98 | 0.36 |
| 2 (256³) | Path-traced (SPP 8) | 908.7 | 1.10 | 0.28 |
| 3 (1024×1024×512) | Lambert + shadow | 456.5 | 2.19 | 0.30 |
| 3 (1024×1024×512) | Path-traced (SPP 8) | 580.3 | 1.72 | 0.33 |

### 관찰

**Render CPU는 모든 케이스에서 0.28–0.36 ms**. 변동성 무의미.
이유: CPU ms는 command-buffer 기록 + submit만 측정 (GPU 비동기). 실제 GPU 작업
시간은 여기 안 잡힘. **GPU 정밀 측정은 D3 Phase 2(GpuProfiler/WebGPUTimer
확장)에서 필요**.

**프레임 시간은 GPU bound + 화면 픽셀 수에 좌우**:
- 96³와 1024³가 비슷한 ms/frame (2.16 vs 2.19) — 볼륨 voxel 수가 아니라
  **AABB가 화면을 덮은 픽셀 수 × march step 수**가 비용을 결정
- 256³는 카메라가 더 멀리 있어 픽셀 적게 차지 → 0.98 ms로 가장 빠름

**PT 모드 트렌드**:
- 96³, 1024³: PT가 Lambert와 **비슷하거나 더 빠름**. Lambert는 max 512 march
  step을 dense하게 돌고, PT는 Woodcock free-flight으로 매질에 따라 조기 종료.
- 256³: PT가 약 10% 느림. SPP 8 × 4 bounce 비용이 dense하지 않은 march보다 큼.

→ PT는 dense 볼륨에서 의외로 **경쟁력 있음**. M4 v0+v1의 algorithm 선택이
실용적이라는 검증.

## 4. 헤드라인 — 이 baseline에서 주장할 수 있는 것

> RTX 4070 / Vulkan 네이티브 / 1280×720 윈도우 환경 기준:
>
> - **1 GB 합성 CT 볼륨이 456 FPS (Lambert) / 580 FPS (Path-traced) 로 동작**
> - VRAM 점유: 1024 MB → 281 MB (M3-3 v0 brick atlas, **72.6% 절감**)
> - SPP 8 + bounce 2 path tracer가 dense 볼륨에서 Lambert와 동등 이상

WASM (브라우저 WebGPU)에서 같은 측정은 **별도 세션에서 반복**. 브라우저 GPU
오버헤드 + ASYNCIFY suspend 비용으로 native 대비 50–70% 정도가 예상되지만
실측이 필요.

## 5. M3-3 v1 streaming에서 노릴 지점

이 baseline이 명확히 드러내는 다음 단계의 가치:

1. **작은 볼륨 case (96³, 256³)에서 brick atlas가 손해**. v1에서 "작은
   볼륨은 dense fallback" 옵션 또는 atlas 최소 크기 추가 검토 가치 있음.
2. **1024³ atlas 280 MB도 여전히 큼**. v1 streaming + LRU로 frustum에 들어
   오지 않은 brick은 atlas에서 evict하면 **실제 live working set만 VRAM 점유**
   가능. 304 slots → frustum 가시 ~50 slots만 resident면 50/512 = 9.8% = **50 MB**
   까지 줄어들 가능성.
3. **현재 측정의 한계**: dense sphere 합성이라 sparsity가 매우 단순. 실
   임상 CT는 환자 외부 air ratio 가 90%+ — 더 좋은 결과 예상.
